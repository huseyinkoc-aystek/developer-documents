# AYSRPAY (Ödeme Alma Sistemi) - Current State Notes

**Date:** 2026-07-09
**Project path:** `/workspace/php/AYSRPAY`
**Purpose (per business owner):** "Ödeme Alma Sistemi" — a debt/payment collection portal. It lets **Gürsel Turizm** (a tour/travel operator, domain `gurseltur.com.tr`) pull outstanding customer balances from its own SAP-based back office over SOAP, email each debtor a personal payment link ("ComfortGo Ödeme Bilgisi"), and let them pay by credit card (3D Secure, Garanti/Yapı Kredi Sanal POS) without logging into anything. A small internal "manager" back office lets AYSTEK/Gürsel staff see customers, debts, payments, and configure emails/contracts.

This app is **not a general-purpose e-commerce app**. Structurally it is a stripped-down fork of a larger AYSTEK B2B/e-commerce codebase (see Known Issues) — most of its scaffolding (categories, menus, multi-language app settings, Ozon marketplace fields, push notification helpers, three mail "themes") is leftover from that parent project and unused here. The only end-to-end business flow that is actually wired up is: **sync debt from Gürsel → email payment link → customer pays by card → record payment → notify Gürsel back.**

**Cross-check:** independently re-verified against source in `LEGACY_GURSEL_APPS_CODEX_REVIEW_2026-07-09.md`, which confirms Garanti is the only active gateway here (Yapı Kredi is dead/disconnected) and adds the AYSTEK Core bounded-context mapping / migration sequence / do-not-migrate list. Read that file alongside this one before planning the migration.

## 1. Overview

- **Framework:** Yii2 `~2.0.45` ("yii2-app-basic" skeleton), PHP `>=7.4`.
- **Primary datastore:** MongoDB (`yiisoft/yii2-mongodb ^3.0`). `config/mongodb.php` points at `mongodb://localhost:27017/aystek_rpay_001`. Every domain model (`User`, `Customer`, `DebtList`, `PaymentList`, `PaymentTransaction`, `Contract`, etc.) extends `\yii\mongodb\ActiveRecord` and uses `collectionName()` instead of `tableName()`.
- **Secondary datastore:** a MySQL connection is still configured (`config/db.php`, `dsn=mysql:host=localhost;dbname=yii2basic`, empty root password) — this is the untouched Yii2 skeleton default and does not appear to back any real model in this app (no ActiveRecord under `models/` or `modules/*/models/` extends `\yii\db\ActiveRecord`). It is wired into `config/console.php` as the console app's only DB, while `mongodb` is **not** bootstrapped for the console app at all (see §6).
- **Session storage:** MongoDB-backed session (`yii\mongodb\Session`), cookie name `_aysRPAY5834AppSessionId`.
- **UI stack:** Bootstrap 5 (`yiisoft/yii2-bootstrap5`), Kartik widgets (`kartik-v/yii2-widgets`, `yii2-grid`, `yii2-dynagrid`, `yii2-detail-view`, `yii2-checkbox-x`, `yii2-bootstrap5-dropdown`), `2amigos/yii2-ckeditor-widget` (rich text editing, used for contract/email bodies), `pctux/yii2-invisible-recaptcha` (Google invisible reCAPTCHA — key hardcoded, see §8).
- **Mailer:** `yiisoft/yii2-symfonymailer` (Symfony Mailer), SMTP transport, credentials hardcoded in `config/web.php` (see §8).
- **No dedicated payment-gateway SDK** is used — Garanti and Yapı Kredi Sanal POS integrations are hand-rolled raw HTTP/cURL + hand-built XML against the banks' legacy POS endpoints (no `mews/pos`, no `omnipay`, etc.). No PDF library is used anywhere in this app (no dompdf/mpdf/tcpdf in composer.json) despite "contract"/"invoice" terminology — contracts are stored and rendered as HTML text, not generated PDFs.
- **Dev tooling:** `yii2-debug`, `yii2-gii` (including a MongoDB model generator config), Codeception (`^5.0`) for unit/functional/acceptance tests.
- **`web/index.php`** sets `YII_ENV` from constants (standard Yii2 basic entry script) — no environment-driven secrets management (`.env`) is used anywhere; all secrets are literal PHP values in `config/*.php` and model/controller code.

## 3. Data model (MongoDB collections)

All models are `\yii\mongodb\ActiveRecord`; "relations" are informal (plain `_id` string references resolved via ad-hoc finder methods, not Yii `ActiveQuery` relations/joins — Mongo has no FK constraints here).

- **`user`** (`app\models\User`, implements `IdentityInterface`) — `name`, `surname`, `full_name`, `email` (unique), `phone`, `photo`, `language`, `password` (Yii security hash), `auth_key`, `group`/`group_id`/`group_sub_id`, `permission_groups` (array of `PermissionGroups` constants), `password_updated_date`, `password_end_date` (defaults to +6 months on create), `user_agreement`/`kvkk` (store the **full contract text snapshot**, not just a boolean+timestamp), `receive_notification`/`receive_email`, `android_notification_tokens`/`ios_notification_tokens` (push-token arrays — vestigial, see §8), `approved`, `suspended`, audit fields.
- **`customer`** (`manager\Customer`) — `name`, `surname`, `full_name`, `email`, `customer_number` + `customer_sub_number` (composite key mirroring Gürsel's SAP "No"/"KalemNo"), `description` (array, populated from Gürsel's `Comment` field split on `+`), audit fields. `getTotalCustomerDebt()` = sum(`debt_list.amount`) − sum(`payment_list.amount`) for the customer.
- **`debt_list`** (`manager\DebtList`) — `customer_id`, `amount`, `currency`, audit fields. This is the collection actually read by the checkout flow (`Customer::getTotalCustomerDebt`) and rewritten wholesale by `RefreshvaluesController::saveGurselCustomer()` whenever Gürsel's reported balance differs from the locally computed total.
- **`customer_debt`** (`manager\CustomerDebt`) — `customer_id`, `currency`, `amount`, `due_date`, audit fields. Structurally near-identical to `debt_list` but has its own controller/CRUD and is **not referenced by any of the payment/notification business logic found** (`Customer`, `RefreshvaluesController`, `UrlfromcheckoutController` all use `DebtList`, never `CustomerDebt`). Likely an earlier iteration or a parallel/legacy debt model — worth confirming with the business owner before deciding which is canonical during migration.
- **`payment_list`** (`manager\PaymentList`) — `customer_id`, `order_id`, `vpos_id` (bank merchant ID that processed it), `amount`, `currency`, `reference_code`, `auth_code`, `payment_summary` (free-text summary incl. order/ref/auth/amount), audit fields. Also hosts most of the payment-flow **status constants** (`PAYMENT_SUCCESS`, `PAYMENT_FAILED`, `LOAD_PAYMENT_PAGE`, `CREATING_VPOS_INFOS`, etc.) even though those are logged into `PaymentTransaction`, not `PaymentList` itself — i.e. business-flow constants live on the wrong model.
- **`payment_transaction`** (`manager\PaymentTransaction`) — append-only audit/state log: `user_id` (actually a customer id), `order_id`, `vp_order_id`, `transaction_id` (one of the `PaymentList::*` status constants), `payment_method`, `ip`, `notification`, `order_note` (free-form: sometimes a human string, sometimes raw `$_POST`, sometimes a full bank XML request/response — see §8 for the PCI implications), audit fields.
- **`email_list`** (`manager\EmailList`) — `customer_id`, `email`, audit fields; multiple emails per customer, deduped via `distinct('email')` when sending notifications.
- **`sent_email`** (`manager\SentEmail`) — persisted copy of every email actually sent (`layout`, `html` template, `from`/`to`/`cc`/`bc`, `subject`, `messages`, `urls`), created by `SentEmail::newEmail()`.
- **`phone_number_list`** (`manager\PhoneNumberList`) — `customer_id`, `country_code`, `area_code`, `phone_number`; model has no business logic attached anywhere found (CRUD only) — SMS notification path does not read from it (see §5).
- **`sent_security_code`** (`service\SentSecurityCode`) — `phone`, `permission_group`, `sent_type`, `security_code`; has `newCode()` but nothing calls it in this app.
- **`contract`** (`manager\Contract`) — `language`, `contract_type` (`user_agreement`, `kvkk`, `terms_and_conditions`, `privacy_policy`, `distance_selling_contract`, `preliminary_information_form`), `contract` (HTML body), audit fields. `getContract($type)` returns the latest-created contract body for the current `Yii::$app->language`.
- **`currency`** (`manager\Currency`) — code, `value` (rate relative to a base), `decimal_places`, `DEFAULT_VALUE_CURRENCY` constant; refreshed daily-on-demand from TCMB by `service\ExchangeRate::currenciesUpdate()`.
- **`app_setting`** (`manager\AppSetting`) — singleton document: multi-language titles/contact messages (en/tr/ru/de/it/ar), logos, `enabled_virtual_pos` flag, social links, and unused `ozon_client_id`/`ozon_api_key`/`ozon_host` fields (Ozon is a Russian e-commerce marketplace — clearly copied from a different, e-commerce-flavored AYSTEK app; nothing in AYSRPAY talks to Ozon).
- **`category`**, **`menu`** (`manager\Category`, `manager\Menu`) — generic storefront/catalog scaffolding (image uploads, block placement, SEO fields) with no consumer in this app's views.
- **`permission_groups`**, **`permission_names`**, **`permissions`** — a granular RBAC data model (group ↔ permission-name ↔ permission mapping) with full CRUD, but the actual access checks in every controller are hardcoded `in_array($x, Yii::$app->user->identity->permission_groups)` checks against 4 constants (`PG_SuperUser`, `PG_Manager`, `PG_Staff`, `PG_Customer`) — this data model is not consulted by the access-control code (see §7).
- **`language`** — simple code/name list backing `SiteController::actionChangelang` and the `Contract` per-language lookup.
- **`session`** — Yii's Mongo-backed session store (framework-managed, not a domain model).

Core entities for the payment-collection domain, summarized: **Customer** (debtor) ↔ **DebtList** (what they owe, synced from Gürsel) ↔ **PaymentList** (what they've paid, synced back to Gürsel) ↔ **PaymentTransaction** (step-by-step log/audit trail of one checkout attempt) ↔ **EmailList/SentEmail** (how they were notified) ↔ **Contract** (the legal texts shown/accepted).

## 4. Business logic & workflows

### 4.1 Debt sync (Gürsel → AYSRPAY)

`modules/service/controllers/RefreshvaluesController::actionGetgurselcustomer()` (HTTP Basic Auth, POST, CSRF disabled) calls `service\Gurselconnection::getDebts()`, which opens a `SoapClient` against `https://sapservice.gurseltur.com.tr/webservices/platetosupplierservice.asmx?WSDL` and invokes `extraEodemeListesi` with **hardcoded credentials** (username/password pair, values redacted here) (`modules/service/models/Gurselconnection.php:28-29`, duplicated at `:46-47` and again in `modules/manager/models/PaymentList.php:186-187`). The response is a JSON string (each customer: `No`, `KalemNo`, `EMail`, `Comment`, `ClientCost`). `saveGurselCustomer()` then, per customer:
1. Finds or creates a `Customer` by `(customer_number, customer_sub_number)`.
2. Overwrites `email`/`description` from Gürsel's data.
3. Adds/refreshes an `EmailList` entry.
4. Compares locally-computed total debt (`Customer::getTotalCustomerDebt`) to Gürsel's `ClientCost`; if different, **inserts a brand-new `DebtList` row for the delta amount** (it does not replace/zero the old rows — `DebtList` rows accumulate; only `DebtList::deleteDebt()` — called when Gürsel reports "no debt" during checkout, see 4.2 — clears them, and it only deletes **one** matching row via `->one()`, not all of them, which is a likely bug if multiple debt rows exist for the same customer).
5. On a new debt row, calls `SendInformation::sendDebtInfo($customer)` to email the payment link.

### 4.2 Payment link → checkout

Entry point: `controllers/UrlfromcheckoutController::actionIndex($cNum, $cSubNum)`, reached via the link emailed in step 4.1.5 (`/urlfromcheckout/index?cNum=...&cSubNum=...`, built with `Url::toRoute(..., true)` — an **absolute URL with the customer's plain account numbers as query params**, no signed/expiring token — see §8).
1. Looks up the `Customer` by `(cNum, cSubNum)`, computes local total debt.
2. If debt > 0, re-confirms with Gürsel (`Gurselconnection::isThereDebt`) — if Gürsel now says there's no debt, deletes the (first matching) local `DebtList` row and shows "You have no debt!"
3. On GET, renders the card-entry form (`views/urlfromcheckout/index.php` → `_vpos_form.php`) with a generated unique order number (`ConverterObject::createUniqueOrderNumber(20)`) and logs a `LOAD_PAYMENT_PAGE` transaction.
4. On POST, calls `setGaranti()` (the active path; a parallel `setYapikredi()` exists but is commented out at the call site, `controllers/UrlfromcheckoutController.php:98`) which builds the Garanti "OOS"/3D-Secure request fields (merchant ID, terminal ID, SHA-512 hash using a hardcoded store key/provision password) and returns them to `renderAjax('garanti_3d_form', ...)`.
5. `views/urlfromcheckout/garanti_3d_form.php` renders an **auto-submitting HTML form containing the raw PAN, CVV2 and expiry** as hidden inputs, POSTed via JS `.submit()` directly to `https://sanalposprov.garanti.com.tr/servlet/gt3dengine` (bank-hosted 3D page from there on). This is the standard non-hosted-field Garanti VPOS integration pattern, but it means the merchant server (`VirtualPosForm`) does hold cardNumber/cvc in cleartext PHP properties and cleartext HTML for the one render, and the browser submits full card data straight to the bank rather than through a bank-hosted iframe (see §8).
6. Bank redirects the browser back to `actionGaranticheck()` (CSRF disabled for this action specifically, `UrlfromcheckoutController::beforeAction`). This reads `mdstatus` from the POST, and if it's a status indicating some level of verification (`1`-`4`), builds and POSTs a **second, server-to-server** XML provisioning request to `https://sanalposprov.garanti.com.tr/VPServlet` (auth via hardcoded provision password + SHA-1/SHA-512 hashes). Only if that server-to-server response says `Transaction/Response/Message == "Approved"` does it call `PaymentList::addPayment()`.
7. `PaymentList::addPayment()` saves the `PaymentList` row, logs a `PAYMENT_SAVED` transaction, then calls the private `sendGurselPayment()`, which opens **another** `SoapClient` to the same `platetosupplierservice.asmx` endpoint and calls `PaymentsSet` (hardcoded credentials again, values redacted here) to tell Gürsel's SAP system the payment was made, logging `PAYMENT_SEND_TO_GURSEL_SUCCESSFUL`/`_FAILED`.
8. `views/urlfromcheckout/payment_result.php` shows a simple success/failure page with the order number.

The Yapı Kredi path (`setYapikredi`, `actionYapikredicheck`) implements the same idea against Yapı Kredi's Posnet XML web service (`https://posnet.yapikredi.com.tr/...`) with its own hardcoded `mid`/`tid`/`pid`/`encKey`, but is **not reachable from the UI** today (the only call site is commented out) — see §8 for a parse-error bug found in its dead code.

### 4.3 Contracts

`controllers/ContractController::actionView($q)` renders whichever contract type `$q` (`Contract::User_Agreement`, `KVKK`, etc.) is currently stored for the active language (`views/contract/view.php`, a single generic template). `User::beforeSave()` snapshots the **full contract HTML text** into `user.user_agreement`/`user.kvkk` at registration time (not just an "I agree" boolean + version pointer), so historical proof-of-consent is preserved per user but contract content is duplicated per user record.

### 4.4 User / auth

`views/user` + `controllers/UserController` is plain Gii CRUD for the `User` collection (create/update/view/index/delete/selectlist for a Select2-style AJAX picker). Login/logout/registration entry (`SiteController`) is the stock Yii2 basic template `LoginForm`, unchanged apart from language handling. There's no self-service password reset flow wired to the `generatePasswordResetToken()`/`removePasswordResetToken()` methods present on `User` (no controller action calls them).

## 6. Scheduled jobs / commands

- `commands/HelloController.php` is the **unmodified Yii2 skeleton example command** (`yii hello/index`) — there are no real, project-specific console commands in this codebase.
- The recurring jobs one would expect (debt refresh, FX-rate refresh, debtor-reminder broadcast) are instead implemented as **authenticated HTTP endpoints** meant to be hit by an external scheduler (cron/Task Scheduler calling `curl` with Basic Auth), not Yii console commands:
  - `POST /service/refreshvalues/exchangerate` — FX rate refresh (`RefreshvaluesController::actionExchangerate`)
  - `POST /service/refreshvalues/getgurselcustomer` — debt sync from Gürsel (`actionGetgurselcustomer`)
  - `POST /service/debt/searcher` — broadcast payment-link emails to all customers with a balance (`DebtController::actionSearcher`)
- No actual OS-level cron/systemd-timer/Task Scheduler definition was found in the repository (none expected — that lives on the server, outside this repo), and there's no `commands/` controller wrapping these for `yii <controller>/<action>` invocation either. This means the "scheduling" is entirely external and undocumented in-repo.
- Because `config/console.php` only wires up the MySQL `db` component and **not** `mongodb`, any future console command that touched the Mongo-backed domain models would fail at runtime unless someone first adds the `mongodb` component to the console config — worth fixing/decision during migration rather than carrying the gap forward.

## 7. Auth & permissions

- **Authentication:** Yii's standard `user` component with `User` (Mongo `ActiveRecord` implementing `IdentityInterface`) as identity class; password hashing via `Yii::$app->security` (bcrypt through Yii's `Security::generatePasswordHash`); `enableAutoLogin` is on. Service-to-service endpoints (`DebtController`, `RefreshvaluesController`) reuse the same `User` collection via `HttpBasicAuth`.
- **Authorization is not real RBAC.** Although `permission_groups`, `permission_names`, and `permissions` collections/CRUD exist (suggesting a group→permission-name→permission design was planned), **no controller consults them**. Instead, essentially every `manager` controller and `UserController` repeats the same hand-rolled block in `behaviors()`:
  ```php
  $allow = false;
  if (!Yii::$app->user->isGuest) {
      if (in_array(PermissionGroups::PG_SuperUser, Yii::$app->user->identity->permission_groups)) $allow = true;
      if (in_array(PermissionGroups::PG_Manager,   Yii::$app->user->identity->permission_groups)) $allow = true;
      if (in_array(PermissionGroups::PG_Staff,     Yii::$app->user->identity->permission_groups)) $allow = false;
      if (in_array(PermissionGroups::PG_Customer,  Yii::$app->user->identity->permission_groups)) $allow = false;
      }
  ```
  i.e. only `SuperUser`/`Manager` can use the back office; `Staff`/`Customer` explicitly cannot. This logic is duplicated verbatim across ~13 controllers rather than centralized (e.g. in a base controller or a real `yii\rbac` `AuthManager`), so any future role change requires editing every controller file individually.
- **No `authManager` component** is configured in `config/web.php`, confirming Yii's built-in RBAC is not actually in play — the `Permissions*` models/controllers are effectively unused scaffolding today.
- **Customer-facing checkout has no authentication at all** — `UrlfromcheckoutController` has an empty `behaviors()` (no `AccessControl`), by design: customers reach it via the emailed link, identified only by `cNum`/`cSubNum` query parameters (see §8 for the security implication).
- **CSRF:** globally on by default; explicitly disabled for the two bank-callback actions (`yapikredicheck`, `garanticheck` in `UrlfromcheckoutController::beforeAction`) and for the two Basic-Auth service endpoints (`DebtController`, `RefreshvaluesController`) — both are reasonable/expected exceptions for machine/bank callers, not oversights.

## 8. Known issues / tech debt

Ordered roughly by severity; payment-data-handling items first since those matter most for the modernization plan.

1. **Full card data (PAN + CVV + expiry) is handled and rendered by the application server, not by a bank-hosted iframe/tokenized field.** `models/VirtualPosForm.php` holds `cardNumber`, `cvc`, `expiryDateMonth/Year` as plain PHP model properties bound straight from the customer's POST, and `views/urlfromcheckout/garanti_3d_form.php:34-39` writes them into **plaintext HTML hidden inputs** (`cardnumber`, `cardcvv2`, ...) that client-side JS auto-submits to the bank. This is a legitimate (if dated) non-hosted-fields VPOS integration pattern, but it puts the merchant's own server/app squarely in **PCI-DSS SAQ D-level card-data scope** (the form is rendered server-side with card values interpolated into the page). Any modernization plan should replace this with the bank's hosted-payment-page/iframe/tokenization flow so raw PAN/CVV never transits AYSTEK's own server or DOM.
2. **Raw request payloads containing bank/card fields are logged into the `payment_transaction.order_note` field.** E.g. `UrlfromcheckoutController.php:388`: `$pTrObj->newTransaction($customerId, $orderId, PaymentList::ATTEMPTING_TO_WITHDRAW_FROM_CARD, ..., $_POST);` persists the **entire raw `$_POST`** array from the bank redirect into MongoDB as free-form `order_note`. For the Garanti path this POST is the bank's own 3D-Secure redirect (mdstatus, cavv, eci, etc. — not raw PAN), but the pattern of "just log the whole request body into a database text field" is risky and should be replaced with an explicit allow-list of fields before any migration, especially since `order_note` is later parsed back out with `SimpleXMLElement`/regex assumptions (`PaymentList::sendingFailedPaymentsReRegister`) that a stray field could break.
3. **Hardcoded production credentials/secrets throughout the codebase**, all committed to source (not env vars/secret manager):
   - Gürsel SAP SOAP credentials (username/password pair, plaintext, values redacted here) — `modules/service/models/Gurselconnection.php:28-29,46-47`, `modules/manager/models/PaymentList.php:186-187`.
   - Garanti VPOS terminal ID, merchant ID, provision password, and 3D store key (all values redacted here) — `controllers/UrlfromcheckoutController.php:292-296` (setGaranti) and again at `:594` (actionGaranticheck's own copy of the provision password).
   - Yapı Kredi Posnet `mid`/`tid`/`pid`/`encKey` (values redacted here) — `controllers/UrlfromcheckoutController.php:140-142,360-363`.
   - SMTP mailer password for `no-reply@gurseltur.com.tr` (value redacted here) — `config/web.php:48`.
   - Google reCAPTCHA secret and Google API key (values redacted here) — `config/web.php:89-90,94`.
   - Yii cookie validation key (value redacted here) — `config/web.php:19`.
   - SMS gateway creds, OneSignal keys, FCM server key (values redacted here) — `modules/service/models/SendInformation.php:27-29,173-174,178-179,226,237`.
   These are all live-looking values (not placeholders) sitting in a codebase that will presumably move to a shared Git history/CI in aystek-core — **must be rotated**, not just relocated to env vars, once this migrates.
4. **The Garanti Sanal POS payment-confirmation callback does not independently verify a bank-issued signature on the initial browser redirect** before acting on `mdstatus` (`UrlfromcheckoutController::actionGaranticheck`, `controllers/UrlfromcheckoutController.php:547-585`). It does perform a second, server-to-server provisioning call to Garanti using a shared secret (`strProvisionPassword`/`SecurityData`/`HashData`) and only records a successful payment if *that* call's response says `Approved` — so the money movement itself is not simply trusted from client input — but the branch logic (which mdstatus values even attempt provisioning) is driven entirely by attacker-visible/POST-able fields with no upfront HMAC check on the incoming redirect. Recommend an explicit review against current Garanti VPOS integration guides (hash/HASHPARAMS verification on the inbound redirect) before porting this flow as-is.
5. **This codebase is a fork of a larger e-commerce/B2B app with substantial leftover dead code and copy-paste residue**, several instances of which are outright broken if ever executed:
   - `modules/manager/controllers/SentemailController.php` imports and instantiates `OrderSummary`, `OrderPayment`, `CustomerLoanRule` (`actionOrderinfo`, lines 155-197) — **none of these classes exist anywhere in this repository** (confirmed via repo-wide search); this action would fatal-error with "Class not found" if ever hit. It also calls `Url::toRoute(['customer/checkout/addpayment', ...])`, a route that doesn't exist in this app either. The same method calls `$model->newEmail($subject, $message, $from, [$to])` (4 positional args) against a signature that expects `($subject, $messages, $urls, $from, $to, ...)` (`SentEmail::newEmail`) — even if the missing classes were stubbed out, the argument order is wrong.
   - `modules/service/models/ClientInfo.php:18,28` imports/instantiates `app\modules\manager\models\IpLocation`, which does not exist in this repo — dead/broken geo-IP logging code, not called from anywhere found.
   - `modules/service/models/SendInformation.php` contains SMS (`SMS_API_USERNAME` value translates to "school-student-info", value redacted here), OneSignal, and FCM push-notification helpers whose branding/icon names ("ana_okulum_mini_icon") point at an unrelated kindergarten-app project. None of these methods are called from anywhere in AYSRPAY. `sendingSms()` additionally has a real bug independent of being dead code: it discards its own `$phoneNumbers` argument and hardcodes a single test number (`SendInformation.php:41`, value redacted here).
   - `modules/manager/models/AppSetting.php` carries `ozon_client_id`/`ozon_api_key`/`ozon_host` fields (Ozon = Russian marketplace) with no corresponding integration code — vestigial from a different app.
   - `Category`/`Menu` modules (models, controllers, full CRUD views) exist with no consumer anywhere in the customer-facing flow.
   - Comment in `UrlfromcheckoutController.php:300-301` literally references the sibling project this was forked from: `"http://localhost/projects/AYSTEKB2BNoSql-V1/web/customer/checkout/creditcard"`.

6. **Two parallel, seemingly-redundant debt models** (`manager\DebtList` vs `manager\CustomerDebt`, each with full CRUD) where only `DebtList` is wired into the real business logic (`Customer::getTotalCustomerDebt`, checkout, Gürsel sync) — needs a decision from the business owner on which is authoritative before migration.
7. **`DebtList::deleteDebt($customerId)` only deletes one (`->one()`) matching row**, not all debt rows for that customer, even though `RefreshvaluesController::saveGurselCustomer()` can insert multiple `DebtList` rows over time for the same customer (it appends a new row per detected delta rather than upserting a single balance row) — if a customer ever has more than one outstanding `DebtList` row, "you have no debt" cleanup will leave stale rows behind.
8. **RBAC is duplicated, not centralized** (see §7) — a full permission-group/permission-name/permission data model exists but is unused; actual authorization is ~13 copies of the same `if (in_array(...))` block. Any role change today means editing every controller.
9. **No environment-based config** — all environment-specific values (DB/Mongo DSNs, mail credentials, bank merchant IDs, API keys) are literal values in versioned `config/*.php` files; there is no `.env`/`params-local.php` split, `web.php` even contains a commented-out **different** production mailer password right next to the live one (`config/web.php:44-48`), suggesting these values have been hand-edited in place across deployments.
10. **Console app cannot touch Mongo data** — `config/console.php` never registers the `mongodb` component (only `db`, the unused MySQL connection), and the only console command present is the stock Yii `hello` example — there is effectively no console/cron tooling for this Mongo-backed app today (see §6).
11. No automated test coverage was found for the payment/checkout flow itself; `tests/` (excluded from deep review per instructions, but the directory listing shows `unit`, `functional`, `acceptance` suites) appears to only exercise the stock Yii2 basic-template `LoginForm`/`ContactForm`/`User` scaffolding that ships with `yii2-app-basic`, not `UrlfromcheckoutController`, `PaymentList`, or the Gürsel integration.
12. No TODO/FIXME/HACK markers were found via repo-wide grep — the technical debt here is entirely implicit (dead imports, hardcoded secrets, copy-paste) rather than self-flagged in comments.

## 9. `vdb_bckp/` folder

`vdb_bckp/aystek_rpay_001/` is a `mongodump`-style backup of the `aystek_rpay_001` MongoDB database: one `<collection>.bson` + `<collection>.metadata.json` pair per collection (`app_setting`, `customer`, `debt_list`, `email_list`, `language`, `payment_transaction`, `session`, `test`, `user`). Sizes are small (largest is `payment_transaction.bson` at 16 KB, `user.bson` at 5.6 KB; several collections — `customer`, `debt_list`, `email_list`, `language`, `session` — are only ~4 KB and `test.bson` is empty), consistent with a development/staging snapshot rather than a full production dump. Metadata files only declare the default `_id_` index per collection (no custom indexes defined anywhere in this database). Per the task's data-handling instructions, the raw `.bson` payloads (which would contain real customer names/emails/phone numbers/debt amounts) were **not opened or read** — only file listing, sizes, and the schema-only `.metadata.json` files were inspected. Treat this directory as containing real (if stale) customer PII and exclude it from any repo copy that leaves controlled AYSTEK infrastructure.

## Summary for migration planning

- **Real, load-bearing business flow to port:** Gürsel SOAP debt sync → `DebtList`/`Customer` → payment-link email (`koble-business/notification-2` theme) → Garanti 3D-Secure checkout (`UrlfromcheckoutController`) → `PaymentList`/`PaymentTransaction` → SOAP payment confirmation back to Gürsel.
- **Everything else** (Category/Menu, Ozon fields, push notification helpers, `olivia`/`simpli` mail themes, the granular Permissions data model, `CustomerDebt`, Yapı Kredi path) is either dead, unused, or of unconfirmed relevance and should be explicitly confirmed with the business owner rather than carried over by default.
- **Highest-priority remediation before/alongside migration:** move all card-data handling to a hosted/tokenized bank integration (item 1), rotate every hardcoded credential (item 3), and decide the fate of the duplicated debt model (item 6) and the unused Permissions RBAC scaffolding (item 8) so the new AYSTEK Core implementation isn't designed around dead structures.
